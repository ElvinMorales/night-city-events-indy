# Indy moderator publication

## Moderator workflow

1. Open the private dashboard over Tailscale. Check the dated organizer evidence and the prefilled event details. A venue calendar can serve as evidence if it lists the specific occurrence and date. Add an evidence URL when the dashboard has no dated source. Use **Edit** for corrections and **Defer** or **Dismiss** for uncertain or duplicate leads.
2. Tap **Approve** to confirm the dated event. Approval records the signed-in moderator and the server time. Unknown optional details can stay blank. Compare related catalog records when the dashboard asks whether the event corrects an existing occurrence or is distinct.
3. Open **Publication batch** and select **Submit approved batch**. The server checks the current catalog, prepares the changes and starts GitHub validation for the proposed revision. The public staging branch contains the approved catalog changes. Private decisions and discovery source rows remain on the moderator host.
4. Expand the changes in the batch while validation runs. The status updates automatically. Once validation succeeds, select **Authorize publication of this revision**. The server records the authorization, promotes the validated SHA while main remains at the expected parent, and starts the existing Pages deployment.
5. The dashboard tracks deployment automatically. A completed deployment can be archived on its own or when submitting the next batch. Use **Resume authorized publication** if dispatch was interrupted, **Retry deployment** for a failed or cancelled Pages run, or **Close superseded release** after main advances and the Pages run has finished.

The discovery timer reads main every six hours. Recheck stale approvals against a current discovery snapshot. Saved decisions remain in the private ledger when observations disappear. Resolve conflicting approvals before resubmitting a batch. The existing manual catalog policy covers explicit cancellations.

## Deployment gates

Obtain approval before pushing the pipeline workflow files, installing the service update, issuing write credentials, enabling automated Pages deployment or changing production events. After approval, perform one supervised smoke test and enable operation without a scheduled trial.

1. Merge the reviewed code into `main` without changing `src/data/events.json`. The validation dispatch workflow must exist on main. Keep the existing manual Pages workflow available. Confirm the default branch name is `main`, the Pages environment accepts main, and repository rules permit the dedicated automation identity to fast-forward main to the validated child. Keep force rewrites and branch deletion disallowed. A rule requiring pull requests or signed commits may require a dedicated narrowly scoped bypass or an alternate publishing design. Verify the applicable rules before enabling writes.
2. Stage a root-owned release at `/opt/indy-discovery/moderator-release` using the reviewed commit. Install the locked dependencies with Node 22 or newer using `npm ci`. Create `/var/lib/indy-discovery/moderation` owned by `indy-discovery:indy-discovery` with mode `0700`. Back up the existing report service definition and any drop-ins. The report should remain on the existing trusted Tailscale Unix socket. Local permissions must prevent untrusted processes from reaching the socket and supplying identity headers. Keep the existing moderator login configuration, runtime directory and socket mode.
3. Install the [systemd drop-in example](systemd/moderator-publication.conf) for `indy-discovery-report.service`, initially without the credential directive. Place the two switches in root-owned `/etc/indy-discovery/publication.env`, initially both `false`. Run `systemd-analyze verify indy-discovery-report.service`, reload systemd and restart only the report. Verify authorized read and unauthorized denial through the existing tailnet path. Enable `INDY_REVIEW_WRITES=true` for review controls.
4. After credential approval, issue a dedicated fine-grained PAT restricted to this one repository with **Contents read/write** and **Actions read/write**, plus required metadata access. A GitHub App installation token with equivalent permissions can also be used if its renewal is wired to the protected service credential. Keep the token out of shell history. Store it in a root-only mode-`0600` file and use systemd `LoadCredential` as shown in the drop-in. The browser receives no GitHub token. Git promotion uses a process environment header restricted to `https://github.com/` and an owner-only temporary bare clone with no persistent secrets. Repository credentials have no Pages, workflow editing, admin or organization permissions. The report service will need outbound HTTPS for GitHub and resolver access.
5. After deployment approval, set repo variable `INDY_MODERATOR_DEPLOY_ENABLED=true` and local switch `INDY_GITHUB_PUBLICATION=true`. Restart only the report to load local settings. Validate access, narrow credential scope, the phone form and origin handling through Tailscale. Complete the supervised workflow using an independently verified real occurrence only if that exact production release is authorized.

For the mobile review update, deploy the same reviewed revision to both the moderator release and the checkout used by the discovery refresher. The hosted refresher adds matched venue and catalog details to new queue snapshots. Run the existing refresh after installation so the dashboard has those details at the current catalog revision. Keep the private decisions file and existing credentials and switches in place.

The private ledger is `/var/lib/indy-discovery/moderation/decisions.json`, written atomically with mode `0600`. A stale lock can remain after a forced termination. Stop the report and verify no moderation request is running before removing only `moderation/.lock`. Preserve backups outside the public repo. Retain staging refs while they are needed to validate, authorize, or recover a release. An authorized repository maintainer can remove old `indy-catalog/*` branches after closure to reduce clutter. Deleting a branch cannot retract public Git history.

## Kill switches and rollback

- For immediate shutdown, stop `indy-discovery-report.service`. Set `INDY_GITHUB_PUBLICATION=false` and restart to keep private reviews available. Set `INDY_REVIEW_WRITES=false` and restart to serve a read-only report. Local switches affect new requests. Inspect Actions and cancel any in-progress dashboard release separately.
- Set `INDY_MODERATOR_DEPLOY_ENABLED=false` to block the Pages build on future dashboard dispatches while retaining manual Pages operation. Cancel any existing run explicitly. Revoke the dedicated credential if local control is lost.
- If a bad release reached main, revert that catalog commit through the normal repository process. Preserve concurrent edits and review conflicts. Validate the resulting main SHA, then use the existing manual Pages dispatch to deploy that exact rollback revision. The existing discovery refresh will read the reverted catalog on its next run. Avoid rewriting main.
- To restore the original report, disable publication, remove the new report drop-in, reload systemd and restart the existing report service using its original `/opt/indy-discovery/report.mjs`. Retain the private ledger for audit or recovery. Restore the previous refresher checkout and report release together if rolling back before any event with unknown optional fields has been published.
- Existing retrieval switches still control discovery. An inaccessible, malformed or incomplete feed retains the previous successful queue.
